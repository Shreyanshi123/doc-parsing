Tough documents test: which parser did best, and why

*Fourteen enterprise-style documents (merged-cell tables, nested tables, tables that continue over pages, forms, a scan, charts + photos, Excel and Word). Every parser was run on the documents it can open and scored against a hand-written answer file.*

1. The short answer

  • No single parser wins everywhere. The best parser changes with the document: PyMuPDF4LLM on merged-header and long documents, Docling and OpenDataLoader on wide and nested tables, smart_pdf on charts, Unstructured on the Word file, MarkItDown on the Excel file.
  • Simple tables, ledgers, forms, wide tables, long reports: all parsers with a text layer score 4.4 to 5.0, so the differences are small and speed should decide.
  • Charts: smart_pdf is first on both chart documents (annual report spread 4.53, mixed page 3.90).
  • Merged-header and nested tables: PyMuPDF4LLM, OpenDataLoader and Docling are best; plain PyMuPDF, hybrid_pdf and smart_pdf are weak (2.9 to 3.9).
  • Scan: PyMuPDF4LLM and Docling read it; parsers without OCR return nothing.
  • Smart Extract on these documents: By document with paid parsers scored 4.4 to 5.0 on 8 of 14, 3.9 to 4.1 on 4 (annual report, mixed page, Excel, Word), and about 3.0 on two merged-header tables. By part scored 3.06 on the nested table. Causes are in section 6.

2. How the test was done

  • Documents: 14 documents generated by scripts/make_enterprise_docs.py. They are synthetic, built to be tough, not copies of real company files. Each has a hand-written answer file.
  • Parsers vs parsers: every document was run through every parser that can open its type (PyMuPDF, PyMuPDF4LLM, Docling, OpenDataLoader, Unstructured, MarkItDown, pdfplumber, Tesseract OCR, hybrid_pdf, smart_pdf, native docx / spreadsheet). 128 runs.
  • Score: 0 to 5, average of the 8 parameters that apply (Text, Table, Chart, Infographic, Numeric, Structure, Completeness, Precision). A crash, timeout or empty output counts as 0.
  • Smart Extract: every PDF three ways (A = By document with paid parsers allowed, B = By part with paid parsers allowed, C = By document with free parsers only); Excel and Word once. 38 runs.
  • Not tested: Azure Document Intelligence (paid, left out on purpose) and the vlm parser (sends every page to the LLM, switched off everywhere).
  • Seconds come from runs where the machine was sometimes busy (the 3-page ledger and 20-page report show inflated times). Use them only to tell fast parsers from very slow ones (Docling is the slowest on most files), not as exact numbers.

Where Smart Extract did well

  • Wide table, ledger, form, contract, 20-page report, invoice, nested table (By document) and the scan: 4.4 to 5.0, close to the best single parser. The scan scored 4.41 in all three configurations.
  • Mixed page with chart and photo: By document paid 3.90, higher than By part (3.79) and free (3.55), because the vision model reads the chart.

Where it lost points, and the cause

  1. clinical_trial_table (3.01 paid, 5.0 free) and financial_statement_multiheader (2.96 paid, 4.86 free). The figure detector reported 1 figure on a one-page PDF that contains no picture, so the file was routed to the charts-and-images group, where smart_pdf is the measured winner. smart_pdf then read the table as a figure with the vision model and also appended the PyMuPDF text and table fragments; the same numbers appear twice, which lowers Precision and Structure. With free parsers only, the file goes to PyMuPDF4LLM and scores 5.0 and 4.86. Note: the cause (table graphics counted as a figure) is inferred from the figure count and the output; I did not step through the detector.
  2. policy_schedule_nested (4.77 By document, 3.06 By part). By part splits the page into pieces; the pieces were read by PyMuPDF and OpenDataLoader separately, so the inner table was cut apart and the outer cell text was repeated across columns.
  3. annual_report_spread (3.98 paid, 3.96 By part, 4.05 free) is below smart_pdf run directly (4.53). Smart Extract did not reproduce the direct smart_pdf score here. Not investigated.
  4. Excel and Word (4.04 and 4.09). The native readers are kept first by the prefer_native rule (another parser must win by more than 0.5). MarkItDown (+0.27, below the margin) and Unstructured (+0.77, above the margin) scored higher.

7. What could be changed (nothing has been changed yet)

  1. Figure detector: do not count table borders / shaded rows as a figure. That alone should send both merged-header tables to a good parser (they scored 5.0 and 4.86 on the free route).
  2. smart_pdf duplicates: when the vision model has read a figure, do not append the PyMuPDF fragments of the same area.
  3. Nested tables in By part: keep a table that contains a table as one piece and read it with PyMuPDF4LLM or OpenDataLoader.
  4. Word: test two or three more Word files before changing the native-first rule.

8. Limits of this test

  • 14 synthetic documents, one copy of each: good for finding weaknesses, not enough for final scores per document type.
  • Answer files are hand-written; a different but valid layout of the same content can lose points.
  • Azure Document Intelligence was not run, so there is no paid-parser comparison on these documents.
  • These scores are not merged into the routing table (measured_scores.json).
